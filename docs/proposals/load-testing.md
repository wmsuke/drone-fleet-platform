# 負荷検証の提案

作成日：2026-09-30
対象：drone-fleet-platform（main `d9ef07a` 時点のコード）

## 提案の要旨

数百台から数千台のフリートを扱えることを、実測値で示せる状態にする。
狙う業種（ドローンやロボットを数百台から千台以上束ねるオーケストレーション）では、台数、送信間隔、遅延、欠損率の実測値が、設計の妥当性を示す直接の証拠になるためである。

提案は次の3点である。

1. 負荷生成器を作り、計測を Phase 2（AWS IoT 接続）の直後から始める。現在のロードマップでは Phase 4 の作業範囲に入っている。
2. 継続負荷のボトルネック特定と改善はローカルで行う。AWS IoT Core では、無料利用枠の範囲で認証、接続レート、同時接続、クラウド経路を確認する。
3. AWS 環境は常時稼働させない。計測ごとに Terraform で作成し、計測後に削除する。負荷生成器にも最大送信件数と最大実行時間を設定する。

AWS 側では月間200,000件をプロジェクトの自主上限とする。これはFree Tierやcreditの残量とは別に適用する安全側の上限であり、10,000台・5秒間隔の継続性能はローカルで検証する。

## 前提と制約

- AGENTS.md の方針により、AWS 対応後もローカルだけで動く構成を維持する。
- README は「1000台規模の性能はPhase 1の保証対象外」と定めている。
- `docs/roadmap.md` の Phase 4 は「100台、1000台への対応は、実測結果を基に判断する」と定めており、計測の手順と目標値は未定である。
- 計測は個人の費用負担で行う。そのため、常時稼働を前提とする計測は選択肢から外す。
- AWS の計測は、実行前に Billing の Free Tier 画面で対象期間と当月残量を確認できた場合だけ行う。
- AWSのFree Tier制度はアカウント作成日とプランで異なるため、固定の無料件数を前提にしない。Billingに表示される有効なオファーまたはcredit残量を実行ごとに確認する。
- 他の用途による当月使用量を含め、ルール起動、アクション、メッセージのいずれも200,000件を超えないようにする。

## 現在の構成で想定するボトルネック

以下はコードを読んで推定したものであり、計測はしていない。
いずれも Phase 1 の範囲では妥当な選択であり、欠陥として挙げるものではない。

| 箇所                                                                                                      | 規模を上げたときに起きると推定すること                                                                                                  |
| --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/telemetry-ingestor/src/app.ts:37-40`（`clientId: "telemetry-ingestor"` 固定）                       | 同じ clientId の接続は先の接続を切断するため、ingestor を同時に1プロセスしか動かせない。受信処理量の上限は1プロセスの処理能力で決まる。 |
| `apps/telemetry-ingestor/src/repository.ts:43-58`（1メッセージごとにトランザクションで upsert と INSERT） | 1,000台が1秒間隔で送ると毎秒1,000トランザクション、1日で約8,600万行になる。                                                             |
| `apps/api/src/repository.ts:15-27`（`telemetry` 全体への `DISTINCT ON`）                                  | 行数の増加に応じて `GET /devices` の応答時間が伸びる可能性がある。実行計画は未確認である。                                              |
| `apps/simulator/src/fleet.ts:27-38`（1プロセスで1台ずつ順に接続）                                         | 台数に比例して起動時間が伸び、1台のマシンで生成できる負荷に上限がある。                                                                 |
| `infra/local` の Mosquitto 1台                                                                            | ローカルでの上限台数は未確認である。                                                                                                    |

## 計測の進め方

### 段階1：ローカルでのボトルネック特定

Docker Compose の構成（Mosquitto、PostgreSQL、ingestor、API）に負荷生成器をつなぎ、台数と送信間隔を段階的に上げる。
指標が悪化し始めた台数を記録し、原因となった箇所を特定して改善し、同じ条件で再計測する。
この「計測、特定、改善、再計測」の記録を、ポートフォリオの主な材料にする。

### 段階2：AWS IoT Core 経由の確認

段階1で改善した構成を AWS IoT Core に接続し、証明書による認証、接続レート、同時接続、クラウド経路を確認する。
AWS では継続的な限界性能を測らず、無料利用枠の範囲に収まる短時間の確認だけを行う。終了後は接続を切り、環境を削除する。

### 計測シナリオ

| シナリオ         | 内容                                                                             |
| ---------------- | -------------------------------------------------------------------------------- |
| **定常送信**     | 全台が接続した状態で、一定間隔のテレメトリ送信を続ける。                         |
| **立ち上げ**     | 接続レートを指定して全台を順に接続し、全台が ONLINE になるまでの時間を測る。     |
| **再接続の集中** | ブローカーを再起動し、全台の再接続が完了するまでの時間と、その間の誤判定を測る。 |

ローカルでは1,000台、3,000台、10,000台と、5秒間隔、1秒間隔を候補とする。

AWS では、同じ月に次の3条件を実行する場合を上限の例とする。

| 目的               |     台数 | 送信間隔 | 時間 | テレメトリ件数 |
| ------------------ | -------: | -------: | ---: | -------------: |
| 通信経路の確認     |    100台 |      5秒 | 10分 |       12,000件 |
| 実用的な短時間試験 |  1,000台 |      5秒 | 10分 |      120,000件 |
| 接続規模の確認     | 10,000台 |     60秒 |  5分 |       50,000件 |
| **合計**           |          |          |      |  **182,000件** |

接続状態などの付随メッセージと再試行分を含めて200,000件を超えないようにする。当月に別の試験を行っている場合は、その使用量を差し引く。

## 計測する指標

| 指標                      | 測り方                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 受信処理量（件/秒）       | 負荷生成器の送信成功数、ingestor の受信・検証成功数、DB の保存成功数を同じ試験IDで記録する。                             |
| 欠損率                    | 試験IDごとに送信成功数と保存成功数を比較し、機体ごとの `sequence` の欠番も確認する。                                     |
| 送信から受信までの遅延    | `received_at` と `device_timestamp` の差を集計する。送信側と受信側の時計同期が前提であり、DB保存完了までの時間ではない。 |
| DB保存時間                | ingestor がメッセージを受け取ってからトランザクションが完了するまでをヒストグラムで記録する。                            |
| 誤った OFFLINE 判定の件数 | OFFLINE への状態遷移をイベントまたはカウンターとして記録し、同じ時間帯の負荷生成器の送信記録と突き合わせる。             |
| `GET /devices` の応答時間 | 計測中に一定の並列数と頻度で呼び出し、p50、p95、p99、エラー率、タイムアウト数を記録する。                                |
| 各プロセスの CPU とメモリ | Docker の統計情報、または EC2 のメトリクスで記録する。                                                                   |

各計測結果には、試験ID、台数、送信間隔、ウォームアップ時間、本計測時間、実行環境（マシンの仕様、リージョン）、試行回数を添える。各条件は原則3回実行する。

合格条件は実装前に決める。初期値の候補は、欠損率1%未満、送信から受信までの遅延p95が2秒未満、`GET /devices`の応答時間p95が500ms未満、APIエラー率1%未満とする。ローカルで基準値を測った後、実態に合わない場合は理由を記録して見直す。

## 負荷生成器に必要な機能

- 担当する deviceId の範囲を指定し、複数プロセスや複数ホストに分けて実行できる。
- 1秒あたりの接続数を指定できる（接続レートの上限に当たらないようにするため）。
- 試験IDと負荷生成器のセッションIDを記録する。
- 送信試行数、送信成功数、送信失敗数、最終 `sequence` を機体ごとに記録する。
- 最大送信件数と最大実行時間に達したら自動停止する。
- AWS 向け実行では、開始前に当月の使用量を入力し、今回の上限を超える設定を拒否する。

負荷生成器は既存シミュレータを置き換えず、`apps/load-generator`として分離する。共通の`packages/protocol`でproductionのテレメトリを検証し、通常のシミュレーションと負荷検証の責務を分ける。

## AWS IoT Core の無料利用枠

2025年7月15日以降に作成したAWSアカウントは、Free/Paid planとcreditを基準に利用可能範囲が決まる。それ以前のアカウントには旧制度のオファーが残っている場合がある。どちらもアカウントごとのBilling表示を正とし、固定の無料件数を前提にしない。

試験前にBilling and Cost Managementで、現在のアカウントプラン、AWS IoT Coreへ適用できるFree Tierまたはcreditの残量、対象期間を確認する。対象外または残量を確認できない場合は試験を実行しない。

Basic Ingestはmessage brokerを経由せずRules Engineへ送信するため、通常のpublish/subscribe経路よりメッセージング費用を抑えられる。ただしRule actionなどは別に計数される。制度変更や他用途の使用量に依存せず停止できるよう、プロジェクトの自主上限を200,000件/月とする。

AWS Budgets は予算アラートとして設定するが、通知には遅延があるため停止装置にはしない。負荷生成器の件数・時間上限を主な停止手段とする。

次のサービスはそれぞれ無料利用枠と課金条件が異なるため、構成を決めた後に個別に確認する。

- CloudWatch Logs
- Lambda、SQS、Kinesis、RDS
- 負荷生成器や受信処理を動かす EC2
- データ転送

## 費用を抑える設計の候補

- **クラウド側の受け取りに Basic Ingest を使う**：メッセージブローカーを経由せず Rules Engine へ送る。ローカルは Mosquitto と MQTT 購読のまま残すため、`apps/telemetry-ingestor/src/ingestion.ts` の検証処理と `repository.ts` の保存処理を、受け取り経路から切り離して両方から使う形にする。現在のコードは受け口（`app.ts`）と検証が分かれているため、この切り離しは既存の構造の延長で行える。
- **複数の計測値を1件のメッセージにまとめる**：件数を減らせるが、通信仕様と遅延特性が変わる。費用削減だけを理由に Phase 2 へ入れず、Phase 3 のバッファ・再送設計と一緒に判断する。
- **AWS Budgets で予算アラートを設定する**：シミュレータや環境を止め忘れた場合の検知に使う。通知には遅延があるため、自動停止の代わりにはしない。
- **件数と時間の二重上限を設定する**：AWS Budgets の通知を待たず、負荷生成器自身が自主上限で停止する。

## ロードマップへの影響

Phase 4 の作業範囲にある「台数を増やした場合の負荷検証」を、Phase 2 の直後へ移す。
以降の Phase 3、4、5 でも同じ負荷生成器と指標で再計測し、変更による性能の変化を記録する。

この変更は `docs/roadmap.md` の改訂を伴う。
AGENTS.md は「通信仕様やサービス間の責務を変える場合は、理由と影響を説明する」と定めているため、経路 C の採用を決めた場合は ADR も追加する。

## 採用しなかった案

| 案                                               | 採用しない理由                                                                                           |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| AWS IoT Core を常時稼働させて計測する            | 無料利用枠を超え、個人の費用負担が発生する。                                                             |
| 現在の構成（MQTT 購読）のまま AWS で継続計測する | メッセージの送信と配信が計数され、無料利用枠を短時間で消費する。                                         |
| ローカルだけで計測を完結させる                   | 証明書認証、クラウドの接続レート上限、クラウド経由の遅延を示せない。狙う業種に対する証拠として不足する。 |

## 未確認の事項

| 事項                                                      | 確認方法                                                                             |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| AWS IoT Core の接続レートなどのアカウント上限             | Service Quotas、または AWS IoT Core の「エンドポイントとクォータ」ページで確認する。 |
| AWS アカウントが12か月無料利用枠の対象か                  | Billing の Free Tier 画面で対象期間と当月残量を確認する。                            |
| 1台の Mac で維持できる MQTT 接続数と、Mosquitto 1台の上限 | 段階1の計測で確かめる。                                                              |
| `GET /devices` の SQL の実行計画                          | PostgreSQL で `EXPLAIN ANALYZE` を実行する。                                         |
| 後段のサービスと EC2 の費用                               | 構成を決めた後に試算する。                                                           |

## 決めてほしいこと

1. 負荷検証を Phase 2 の直後へ前倒しするか。
2. クラウド側の受け取りに経路 C（Basic Ingest と IoT Rule）を採用するか。採用する場合、ingestor の検証処理と保存処理の切り離しが必要になる。
3. ローカル計測の合格条件。初期候補は欠損率1%未満、受信遅延p95が2秒未満、API応答時間p95が500ms未満、APIエラー率1%未満とする。
4. ローカル計測のブローカーを Mosquitto のまま使うか、クラスタ構成を取れるブローカー（EMQX など）に替えるか。

## 対象外とするもの

- コマンドの一斉送信の計測。グループ操作は Phase 4 で実装するため、その後に計測する。
- 本番運用を想定した常時稼働環境と、その可用性設計。
- PX4 SITL など飛行シミュレータの機体を混ぜた計測。Phase 7 で扱う。
