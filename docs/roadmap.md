# ロードマップ

Backend、AWS、IoTの実装から始め、Edge、ROS 2、ドローンシミュレータとの接続へ範囲を広げる。

各Phaseで動作する状態をリリースする。AWS対応後も、ローカルだけで試せる構成を維持する。

## 現在の状況

Phase 0の準備中。リポジトリを作成し、設計文書を整備している。

日付による期限は設けず、各Phaseの完了条件を満たした時点で次へ進む。個別の作業と進捗はGitHub Issueで管理する。

## Phase 0：開発基盤

TypeScriptのモノレポと、開発・検証に必要な環境を整える。

### 作業範囲

- pnpm workspaceとTypeScriptの共通設定
- Docker Composeの基本構成
- Mosquittoの起動と送受信確認
- 環境変数と秘密情報の管理
- GitHub Actionsによるlint、型チェック、テスト、ビルド
- README、AGENTS.md、設計文書、初期のADR
- ライセンスの選定と記載

### 完了条件

- 共通の開発コマンドを実行できる。
- Docker ComposeでMosquittoを起動し、MQTTの送受信を確認できる。
- PRで品質チェックが実行される。
- 構成、開発手順、秘密情報の扱いが文書化されている。

## Phase 1：ローカルで動く最小構成

リリース：`v0.1.0`

仮想ドローン10台の状態を確認し、遠隔コマンドの受領まで追跡できるようにする。

### 作業範囲

- MQTTトピックとメッセージの型・検証
- 仮想ドローン10台のシミュレータ
- テレメトリの受信と保存
- デバイス登録
- LWTと最終受信時刻による接続状態の判定
- デバイス一覧・詳細・履歴のAPI
- 帰還・再起動コマンドとACK
- ダッシュボード
- 結合テストとデモ

### 完了条件

- clone後、`docker compose up`で全サービスが起動する。
- AWSアカウントや実機を用意せずに試せる。
- 仮想ドローン10台が約5秒ごとにテレメトリを送信する。
- 一覧と詳細画面で接続状態や計測値を確認できる。
- 切断した機体がオフラインとして表示される。
- コマンドを送信し、ACKと履歴を確認できる。
- シミュレータからAPIまでのデータ経路をCIで検証できる。
- READMEに起動手順、画面例、対応範囲と制約を掲載している。

## Phase 2：AWS IoT接続

リリース：`v0.2.0`

ローカル構成に加え、AWS IoT Coreを経由する通信経路を用意する。

### 作業範囲

- TerraformによるAWS環境の構築
- AWS IoT Thingsとデバイスごとの証明書
- mTLS接続とIoT Policy
- シミュレータのAWS接続
- クラウド側のテレメトリ受信とコマンド送信
- 環境の作成・削除手順と費用の確認方法

### 完了条件

- デバイスごとに異なる認証情報で接続できる。
- 他のデバイスのトピックへの不正な操作を拒否できる。
- AWS経由でテレメトリとコマンド・ACKを確認できる。
- 証明書をリポジトリへ保存せずに環境を再現できる。
- AWS環境を削除する手順がある。
- ローカル構成も引き続き動作する。

## Phase 3：通信断からの復旧

リリース：`v0.3.0`

通信が途切れてもデータを保持し、再接続後に送信を再開できるようにする。

### 作業範囲

- 再接続と待機時間の制御
- SQLiteなどを使った永続バッファ
- 通信断中の保存と再接続後の送信
- セッション識別と連番の扱い
- 重複排除と冪等な処理
- コマンドの有効期限と再送方針
- バッファ容量の上限と上限到達時の動作

### 完了条件

- 通信断中のテレメトリを設定した容量の範囲内で保持できる。
- プロセスを再起動しても未送信データが残る。
- 再接続後に蓄積データを送信できる。
- 同じデータを再送しても、重複して処理されない。
- 古いコマンドや重複コマンドの扱いをテストで確認できる。
- 通信断から復旧までのデモと、保持できない条件を文書に残している。

## Phase 4：複数機体の運用

リリース：`v0.4.0`

グループ単位の操作と、コマンド・異常の追跡を追加する。

### 作業範囲

- 機体のグループ分け
- 複数機体へのコマンド送信
- コマンドの実行完了・失敗の追跡
- アラート
- 操作の監査ログ
- 台数を増やした場合の負荷検証

### 完了条件

- グループを指定してコマンドを送信できる。
- 対象機体ごとの受領・完了・失敗を確認できる。
- 一部の機体が応答しない場合も結果を追跡できる。
- アラートの発生条件と解除条件が定義されている。
- 誰が、いつ、どの機体へ操作したかを記録できる。
- 検証した台数、送信間隔、処理遅延、実行環境を記載している。

100台、1000台への対応は、実測結果を基に判断する。

## Phase 5：OTAと段階的な配信

リリース：`v0.5.0`

デバイス上のソフトウェアを少数台から更新し、結果を見ながら対象を広げられるようにする。

### 作業範囲

- ソフトウェアバージョンの管理
- 配信物の検証
- 配信対象と進捗の管理
- 少数台への先行配信
- 段階的な配信
- 失敗時の停止、再試行、ロールバック

### 完了条件

- 対象機体と配信するバージョンを指定できる。
- 少数台の結果を確認してから配信範囲を広げられる。
- 機体ごとの成功・失敗・未完了を確認できる。
- 失敗時に配信を停止できる。
- 戻せる条件と戻せない条件を文書化し、ロールバックを検証できる。

最初はシミュレータまたはEdge Agentのソフトウェア更新を対象とする。飛行制御用ファームウェアの更新は別途検討する。

## Phase 6：ROS 2連携

リリース：`v0.6.0`

ROS 2とMQTTの間を接続するBridgeを追加する。

### 作業範囲

- node、topic、service、action、DDS、QoSの理解
- バッテリー、位置、診断情報の変換
- MQTTコマンドからROS 2への操作
- ROS 2側の状態と通信エラーの扱い

### 完了条件

- ROS 2のデータを既存の通信形式へ変換できる。
- ダッシュボードからROS 2由来の状態を確認できる。
- コマンドの受領とROS 2側の実行結果を区別して追跡できる。
- Bridgeの起動方法とメッセージの対応関係を文書化している。

C++は必要になった範囲で使用する。

## Phase 7：ドローンシミュレータ連携

リリース：`v0.7.0`

飛行シミュレータの機体をFleet Platformへ接続する。

### 作業範囲

- Gazebo、PX4 SITL、ArduPilot SITLなどから構成を選定
- シミュレータとROS 2・Bridgeの接続
- 位置、バッテリー、飛行状態、エラーの取得
- 対応する遠隔操作の検証

### 完了条件

- シミュレータ上の機体をダッシュボードで確認できる。
- 飛行に伴う位置や状態の変化が反映される。
- 対応するコマンドと制約が文書化されている。
- 起動から操作までを再現できるデモがある。

## Phase 8：AIによる運用支援

リリース：`v1.0.0`

蓄積したテレメトリや操作履歴を使い、異常の調査を支援する。

### 作業範囲

- ログとインシデントの要約
- 異常が多い機体の抽出
- 同じ型式や条件での類似事象の調査
- 保守に向けた確認事項の提示

### 完了条件

- 回答から根拠となったデータや時刻を確認できる。
- データから分かる事実と推測を区別して表示する。
- データが不足している場合は、その範囲を説明する。
- 代表的な問い合わせと期待する結果を用意し、回答を検証できる。

初期段階では調査と説明を対象とする。AIによる自動操作は、このPhaseの完了条件に含めない。

## 進め方

- 実装はGitHub Issue単位で進める。
- 依存する変更をマージしてから次のIssueに着手する。
- 各リリースで起動手順とデモを更新する。
- 後続Phaseの詳細は、着手時にそれまでの実装を踏まえて見直す。
- 設計を変更した場合は関連文書を更新し、判断の背景が必要なものはADRに残す。
