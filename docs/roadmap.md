# ロードマップ

Backend、AWS、IoTの実装から始め、Edge、ROS 2、ドローンシミュレータとの接続へ範囲を広げる。

各Phaseで動作する状態をリリースする。AWS対応後も、ローカルだけで試せる構成を維持する。

## 現在の状況

Phase 2まで完了した。Docker Composeによるローカル構成に加え、AWS IoT CoreへmTLS接続し、機体単位のIoT Policyで制限したtelemetry・status・command・ACKの経路を利用できる。ローカル構成はAWS projectや証明書なしで引き続き利用できる。次はPhase 2.5の負荷検証を進める。

日付による期限は設けず、各Phaseの完了条件を満たした時点で次へ進む。個別の作業と進捗はGitHub Issueで管理する。

## Phase 0：開発基盤

TypeScriptのモノレポと、開発・検証に必要な環境を整える。

### 作業範囲

- pnpm workspaceとTypeScriptの共通設定
- Docker Composeの基本構成
- Mosquittoの起動と送受信確認
- 環境変数と秘密情報の管理
- GitHub Actionsによるlint、型チェック、テスト、ビルド
- README、AGENTS.md、設計文書、初期のADR
- ライセンスの選定と記載

作業範囲はすべて実施済みである。アプリの各ディレクトリはプレースホルダーであり、機能実装はPhase 1から開始する。

### 完了条件

- 共通の開発コマンドを実行できる。
- Docker ComposeでMosquittoを起動し、MQTTの送受信を確認できる。
- PRで品質チェックが実行される。
- 構成、開発手順、秘密情報の扱いが文書化されている。

- 一覧と詳細画面で接続状態や計測値を確認できる。
- 切断した機体がオフラインとして表示される。
- コマンドを送信し、ACKと履歴を確認できる。
- シミュレータからAPIまでのデータ経路をCIで検証できる。

## Phase 2.5：負荷検証

Phase 2のAWS IoT接続後に、ローカル構成の継続負荷とAWS経路の短時間確認を行う。

### 作業範囲

- 試験ID、送信件数、受信件数、保存件数を記録できる負荷生成器
- ingestorの受信・検証・DB保存時間と失敗件数の計測
- APIのp50、p95、p99、エラー率、タイムアウト数の計測
- 1,000台、3,000台、10,000台を候補としたローカル負荷試験
- AWS IoT Coreでの証明書認証、接続レート、同時接続、クラウド経路の確認
- 改善前後を同じ条件で比較できる試験記録

詳細な試験条件と指標は[負荷検証の提案](proposals/load-testing.md)に記載する。

### AWS利用時の制約

- AWS側は無料利用枠の対象期間と当月残量をBillingで確認できた場合だけ実行する。
- 月間200,000件をプロジェクトの自主上限とする。
- 負荷生成器に最大送信件数と最大実行時間を設定する。
- AWSでは継続的な限界性能を測らず、認証、接続、短時間のデータ到達を確認する。
- CloudWatch、Lambda、SQS、Kinesis、RDS、EC2、データ転送は個別に無料利用枠を確認する。
- 試験後に接続を切り、作成したAWS環境を削除する。

### 完了条件

- ローカルで負荷を段階的に増やし、最初に悪化する指標と原因を記録している。
- 送信、受信、検証、保存の各段階を区別して欠損や失敗を確認できる。
- 各条件を原則3回実行し、実行環境と試験条件を結果に添えている。
- 改善前後を同じ条件で再計測している。
- AWS側の総使用量が自主上限内であり、追加料金が発生していないことを確認している。
- AWS無料利用枠の対象外だった場合は実行せず、その旨を記録している。

## Phase 3：通信断からの復旧

リリース：`v0.3.0`

通信が途切れてもデータを保持し、再接続後に送信を再開できるようにする。

配送保証、SQLiteからの削除条件、重複排除、commandの期限とoutboxの設計は[ADR 0005](adr/0005-delivery-and-recovery.md)に記録した。#109でtelemetryのsessionIdを追加し、#110でsimulatorのSQLite永続バッファを追加した。保存確認に基づく削除、再送、重複排除などは#111以降で実装する。

### 作業範囲

- 再接続と待機時間の制御
- SQLiteなどを使った永続バッファ
- 通信断中の保存と再接続後の送信
- セッション識別と連番の扱い
- 重複排除と冪等な処理
- コマンドの有効期限と再送方針
- バッファ容量の上限と上限到達時の動作

### 完了条件

- 通信断中のテレメトリを設定した容量の範囲内で保持できる。
- プロセスを再起動しても未送信データが残る。
- 再接続後に蓄積データを送信できる。
- 同じデータを再送しても、重複して処理されない。
- 古いコマンドや重複コマンドの扱いをテストで確認できる。
- 通信断から復旧までのデモと、保持できない条件を文書に残している。

## Phase 4：複数機体の運用

リリース：`v0.4.0`

グループ単位の操作と、コマンド・異常の追跡を追加する。

### 作業範囲

- 機体のグループ分け
- 複数機体へのコマンド送信
- コマンドの実行完了・失敗の追跡
- アラート
- 操作の監査ログ
- 台数を増やした場合の負荷検証

### 完了条件

- グループを指定してコマンドを送信できる。
- 対象機体ごとの受領・完了・失敗を確認できる。
- 一部の機体が応答しない場合も結果を追跡できる。
- アラートの発生条件と解除条件が定義されている。
- 誰が、いつ、どの機体へ操作したかを記録できる。
- 検証した台数、送信間隔、処理遅延、実行環境を記載している。

100台、1000台への対応は、実測結果を基に判断する。

## Phase 5：OTAと段階的な配信

リリース：`v0.5.0`

デバイス上のソフトウェアを少数台から更新し、結果を見ながら対象を広げられるようにする。

### 作業範囲

- ソフトウェアバージョンの管理
- 配信物の検証
- 配信対象と進捗の管理
- 少数台への先行配信
- 段階的な配信
- 失敗時の停止、再試行、ロールバック

### 完了条件

- 対象機体と配信するバージョンを指定できる。
- 少数台の結果を確認してから配信範囲を広げられる。
- 機体ごとの成功・失敗・未完了を確認できる。
- 失敗時に配信を停止できる。
- 戻せる条件と戻せない条件を文書化し、ロールバックを検証できる。

最初はシミュレータまたはEdge Agentのソフトウェア更新を対象とする。飛行制御用ファームウェアの更新は別途検討する。

## Phase 8：AIによる運用支援

リリース：`v1.0.0`

蓄積したテレメトリや操作履歴を使い、異常の調査を支援する。

### 作業範囲

- ログとインシデントの要約
- 異常が多い機体の抽出
- 同じ型式や条件での類似事象の調査
- 保守に向けた確認事項の提示

### 完了条件

- 回答から根拠となったデータや時刻を確認できる。
- データから分かる事実と推測を区別して表示する。
- データが不足している場合は、その範囲を説明する。
- 代表的な問い合わせと期待する結果を用意し、回答を検証できる。

初期段階では調査と説明を対象とする。AIによる自動操作は、このPhaseの完了条件に含めない。

## 進め方
