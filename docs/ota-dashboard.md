# OTAの段階配信画面

#174でdashboardの`/deployments`と`/deployments/:deploymentId`を追加した。[配信受付](deployments-api.md)、[段階承認・停止/再開](ota-rollout.md)、[復旧](ota-recovery.md)、[人間介入](ota-interventions.md)の既存APIを使う。通信契約・評価条件・復旧許可・認証の境界は変更しない。

## 表示と操作

1. 「OTA配信」で登録時に検証済みのreleaseを選ぶ。version/platform/releaseId/digest/buildIdを確認し、機体IDと任意のグループを指定する。release選択肢は既存APIの最新100件である。
2. 対象は重複を除いた1〜100台。機体IDのASCII順で、省略時は1台/3台/残りに分ける。任意の段階台数（例`1,3,6`）は1〜10段階で全対象と合計を一致させる。確認画面に具体的な機体と段階を固定し、明示したstagesとgroupIds/deviceIdsを送る。確認後のグループ変更で対象が変わる場合は、APIのstage照合で拒否する。
3. 固定分母、失敗率10%以上・結果不明/integrity違反での停止、開始300秒/結果600秒、13標本/60秒health、同時2台を確認して受付する。方針を弱める入力は追加していない。受付後はまだ承認待ちである。
4. 詳細の「操作理由コード」に理由を入力し、段階承認・停止・再開・判断対応を確認する。先行開始も後続昇格も承認が必要。操作ごとに確認・チェックを挟み、Escapeまたは取消で送信せず戻れる。
5. 対象機体の「根拠・履歴・復旧」で、配送/適用/評価、attempt/command/fence、期限、現在版/boot、評価根拠、保存event、拒否・衝突を確認する。復旧候補の場合だけ再試行/rollbackを確認できる。保持した旧版・信頼根・互換性・予約・fence等の最終許可はAPIが再検証する。

HTTP 202は受付のみ。STOPPINGは停止要求中、PAUSEDは配信処理の停止確認済みであり、機体の物理的安全停止ではない。rollbackのWAITING/RUNNINGとSUCCEEDEDを区別し、旧版の回復成功を元releaseの更新成功へ数えない。判断対応の終了でも停止latch・予約・評価を解除しない。

## 観測と安全側の制御

詳細と介入履歴は5秒ごとに取得し、「最新状態を取得」でも照会できる。更新中、取得エラー、未取得、不正な応答、要求開始から10秒以上経過した表示から新しい操作を送らない。HTTP cacheを使わず、UIはサーバーのevaluatedAtと要求開始からのmonotonicな経過時間を使う。応答の取得にかかった時間も保守的に含め、端末観測が15秒以上古くなれば復旧や昇格を無効にする。ブラウザ表示は安全保証・権限判定ではなく、APIが操作transactionで再検証する。

復旧候補はPAUSED、前attempt FAILED、直接STATE終端と現在の版/boot一致、新鮮なINVENTORY・readiness・復旧予算が確認できる場合に限る。UNCERTAIN、適用継続の可能性、観測欠落、表示が切り詰められた根拠、回数上限・予算不足では新attemptを許可しない。retryは適用前DOWNLOAD_FAILEDだけ、rollbackは現在版と異なる既知正常版の確認を要求する。署名・artifactの実在を画面から推測しない。

表示は1ページ20台で、URLの`targetPage`と`stage`に対象ページ/段階を残す。ページを切り替えても固定分母や昇格判定は全対象で行う。APIは既存の上限100台を一括で返し、クライアントで描画をページ分割する。試行根拠は展開した行だけ描画し、event・評価・診断は各APIの上限を明記する。eventは既定20件で、「根拠を100件まで読み直す」から画面内で拡張し、URLの`evidenceLimit=100`に保持する。全根拠が揃って初めて復旧候補を再判定し、100件でも切り詰められていれば復旧を有効化しない。別タブのAPI照会への導線も設け、範囲外の証拠を表示済みと扱わない。全履歴の無制限exportは追加していない。

配信一覧はcreatedAt/ID降順で20件ずつ取得する。同時刻の配信を欠落させないため、APIへ`beforeId`と`nextBeforeId`を追加した。`nextBefore`/`nextBeforeId`を次要求の`before`/`beforeId`に渡す。従来のbeforeだけの呼出しも維持する。IDだけのcursorは400で拒否する。介入履歴は既存の時刻/ID cursorでページングする。

## 二重要求と再読み込み

最終確認後、送信前に操作種類・対象ID・正規化本文・Idempotency-KeyをsessionStorageへ保存する。保存できなければ送信しない。連打を同期的に抑止し、POSTの自動再送はしない。保存内容は同じタブ・API接続先で保持する。

通信断、5xx、不正応答、key衝突など受付結果が不明な間は、新しい要求を作らない。再読み込みや配信詳細への移動後も「同じ要求で受付を確認」から同じkey・本文だけを再送し、自動送信しない。明確な4xx拒否は理由コードを表示し、最新状態を確認してから新しい操作を確認し直す。永続化されたUNAVAILABLEは拒否事実として表示し、復旧成功にしない。保存領域の破損・変更・削除失敗時も新操作を止め、履歴と保存領域の確認を案内する。

sessionStorageは本人確認・改ざん耐性・別タブ間の排他ではない。別タブ/利用者からの競合や手動改変に対する最終gateはAPIのidempotency/lock/状態/予算検証である。

## 人間介入・audit

必須承認と障害対応、未終了・旧操作の詳細欠落を別表示にする。anonymousは本人・承認権限未確認と表示する。作業時間/費用のnullは未取得であり、0を表示しない。報告値だけを自己申告時間として表示し、server受付開始/終了の経過を作業時間へ換算しない。

判断対応終了は停止維持・現地引き継ぎ・同deploymentの対応開始後に承認された復旧要求への引き継ぎを選び、理由を必須とする。時間は取得した場合だけ任意で報告する。開始/操作と終了のaudit、deploymentの監査検索、復旧結果・対象snapshotへ移動できる。介入ありを自律完了へ読み替えず、履歴欠落を自律完了の証明にもしない。

## 起動・検証・未確認範囲

既存のVITE_API_BASE_URLと配信物/信頼根/API設定を使用する。APIのOTA管理routeが無効なら取得エラーとなり、画面から裏で有効化しない。本人認証・RBACは未実装であり、外部公開・実機運用は対象外である。

画面/操作制御テストでは、受付preview、必須理由、二重送信、通信断後の同じ要求・再読み込み、段階昇格、100台のページ表示、結果不明/古い観測/不完全根拠/予算不足の拒否、rollback表示、介入/audit、API失敗、ラベル・表見出し・focus/キーボード取消を検証する。複雑な応答を検証するため、既にリポジトリで使用中のZodをdashboardの直接依存へ追加した。

専用PostgreSQLの結合テストでは、実API応答を画面schemaで検証し、復旧観測の版/bootと同時刻cursorを確認する。Safariでも書き込みを拒否するサンプルAPIで一覧・詳細・100台のページ切替・介入履歴を目視した。これは実端末や実AWSの更新検証ではない。10台の実更新と全障害の横断E2Eは#175に残し、KPI集計・DB長期保管/検索性能の計測は今回追加しない。
