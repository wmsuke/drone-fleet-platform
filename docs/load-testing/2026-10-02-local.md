# ローカル段階負荷試験（2026-10-02）

Issue #63の条件で、Docker Compose上のMosquitto、telemetry-ingestor、PostgreSQL、APIを対象に段階負荷を実施した。高負荷をAWSへ送らず、すべてローカルで計測した。

## 実行環境と方法

- Apple M2（8 logical CPU）、メモリ16 GiB
- macOS 14.5、OrbStack 2.2.3、Docker Engine 29.4.0
- PostgreSQL 17 Alpine、Node.js 22 Alpine
- generator起動猶予15〜30秒、ウォームアップ5秒、計測30秒、最大クールダウン180秒
- 1シャード500台、接続レート500台/秒、原則として各条件3試行
- APIは`GET /devices`を1秒ごとに呼び、response bodyを最後まで受信した時点で応答時間を確定し、2秒でタイムアウトとした
- 各generatorが担当する全機のMQTT接続を完了したことをready markerで確認してからウォームアップする
- 全DB保存件数が15秒間変化しない場合は、生成側とシステム側の差分を残して待機を終了する

全workerで共通の計測開始・終了時刻を使い、warmup中の送信をgenerator、ingestor、DB集約から除外した。API probeとCPU・メモリ収集も本計測区間だけ実行した。送信成功、MQTT受信、検証成功、DB保存成功、実保存件数を同じ`testId`で突き合わせた。受信遅延はdevice timestampからMQTT受信まで、DB保存時間はMQTT受信からINSERT完了までを別に集計した。

API probeをresponse headers到着ではなくbody受信完了まで計測するよう修正し、3,000台・1秒間隔と10,000台・5秒間隔を3試行ずつ再計測した。API p95は前者が208〜231ms、後者が183〜415msで、いずれも500ms未満だった。傾向と合否に大きな変化がなかったため、他条件は再計測していない。

10,000台・1秒間隔は、warmup中に発生したDB backlogを計測終了後も処理し続け、計測対象の約30万件を保存できなかった。telemetry-ingestorは最大CPU 358%、最大メモリ2.3 GiBまで増えた。同じ失敗を繰り返す意義がなくホスト負荷も大きいため、追加2試行は行わなかった。安定して初期基準を満たした最大送信レートは3,000台・1秒間隔である。合格基準は変更していない。

## ボトルネックと改善

最初の10,000台・1秒間隔では、20個のgeneratorコンテナが同時に同じイメージをビルドした。起動がずれ、送信成功232,835件に対してDB保存が220,975件で停止した。欠損率は5.09%で、生成側の起動処理が計測条件へ混入していた。

runnerを変更し、generatorとreportのイメージを事前に一度だけビルドした。さらに全generatorのMQTT接続完了をready markerで確認し、全worker共通の計測窓まで5秒warmupを流すよう修正した。warmupデータは各指標から除外した。これは生成・計測側の改善であり、telemetry-ingestorの処理性能を改善したものではない。

システム側では次の飽和が残る。

- 3,000台・1秒間隔ではDB保存p95が30〜60秒へ増えた。
- 10,000台・5秒間隔ではDB保存p95が1〜30秒で変動し、body受信完了までのAPI p95も最大415msとなったため限界に近い。
- 10,000台・1秒間隔ではwarmupのDB backlogを解消できず、計測対象を保存できなかった。
- 完走条件のPostgreSQL実行計画は、latest telemetry抽出、devicesとのLEFT JOIN、deviceId順ソートを含む実際の`GET /devices`相当SQL全体を対象とした。実行時間は1,000台で7〜37ms、3,000台で24〜144ms、10,000台・5秒間隔で57〜67msだった。
- 共通計測窓に限定した誤OFFLINEは全完走試行で0だった。

次の改善候補は、telemetry-ingestorの1メッセージ1トランザクションをバッチ保存へ変更することと、接続状態更新をテレメトリ履歴の保存待ちから分離することである。挙動変更が大きいため、このIssueでは計測基盤と限界の記録までとし、別Issueで同条件を再計測する。

## 再現手順

```bash
LOAD_DEVICE_COUNT=10000 \
LOAD_TELEMETRY_INTERVAL_MS=1000 \
LOAD_MEASUREMENT_MS=30000 \
LOAD_GENERATOR_STARTUP_SECONDS=30 \
LOAD_WARMUP_SECONDS=5 \
LOAD_COOLDOWN_SECONDS=180 \
LOAD_TRIAL=1 \
pnpm load:test:local
```

各試行の`summary.json`には条件、送受信・保存カウンター、遅延、API結果、コンテナ別最大CPU・メモリ、合否を保存する。`postgres-explain.json`には`GET /devices`相当SQL全体の実行計画を保存する。生の結果はサイズが大きく機体ごとの明細を含むためGit管理外とし、本書へ集約値を残す。
