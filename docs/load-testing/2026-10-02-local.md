# ローカル段階負荷試験（2026-10-02）

Issue #63の条件で、Docker Compose上のMosquitto、telemetry-ingestor、PostgreSQL、APIを対象に段階負荷を実施した。高負荷をAWSへ送らず、すべてローカルで計測した。

## 実行環境と方法

- Apple M2（8 logical CPU）、メモリ16 GiB
- macOS 14.5、OrbStack 2.2.3、Docker Engine 29.4.0
- PostgreSQL 17 Alpine、Node.js 22 Alpine
- ウォームアップ5秒、計測30秒、最大クールダウン180秒
- 1シャード500台、接続レート500台/秒、各条件3試行
- APIは`GET /devices`を1秒ごとに呼び、2秒でタイムアウトとした
- DB保存件数が15秒間変化しない場合は、生成側とシステム側の差分を残して待機を終了する

送信成功、MQTT受信、検証成功、DB保存成功、実保存件数を同じ`testId`で突き合わせた。CPUとメモリは計測中に1秒間隔で`docker stats`から取得した。受信遅延はdevice timestampからMQTT受信まで、DB保存時間はMQTT受信からINSERT完了までを別に集計した。

## ボトルネックと改善

最初の10,000台・1秒間隔では、20個のgeneratorコンテナが同時に同じイメージをビルドした。起動がずれ、送信成功232,835件に対してDB保存が220,975件で停止した。欠損率は5.09%で、生成側の起動処理が計測条件へ混入していた。

runnerを変更し、generatorとreportのイメージをウォームアップ前に一度だけビルドしてから全シャードを起動した。同条件の再計測では3試行とも送信・受信・保存件数が一致し、欠損率は0%になった。これは生成・計測側の改善であり、telemetry-ingestorの処理性能を改善したものではない。

システム側では次の飽和が残る。

- 3,000台・1秒間隔からDB保存p95が5〜10秒へ増えた。
- 10,000台・1秒間隔ではDB保存p95が81〜93秒、telemetry-ingestorの最大CPUが106〜263%、最大メモリが1.4〜1.5 GiBとなった。
- 同条件の`GET /devices`用クエリは10,000行を返し、PostgreSQLの実行時間が122〜136msだった。第2試行ではAPI p95が589.7msとなった。
- DB保存が遅れると最終受信時刻の更新も遅れ、送信中の機体がOFFLINEへ遷移した。10,000台・5秒間隔でも752〜2,000件、10,000台・1秒間隔では全10,000件で発生した。

次の改善候補は、telemetry-ingestorの1メッセージ1トランザクションをバッチ保存へ変更することと、接続状態更新をテレメトリ履歴の保存待ちから分離することである。挙動変更が大きいため、このIssueでは計測基盤と限界の記録までとし、別Issueで同条件を再計測する。

## 再現手順

```bash
LOAD_DEVICE_COUNT=10000 \
LOAD_TELEMETRY_INTERVAL_MS=1000 \
LOAD_MEASUREMENT_MS=30000 \
LOAD_WARMUP_SECONDS=5 \
LOAD_COOLDOWN_SECONDS=180 \
LOAD_TRIAL=1 \
pnpm load:test:local
```

各試行の`summary.json`には条件、送受信・保存カウンター、遅延、API結果、コンテナ別最大CPU・メモリ、合否を保存する。`postgres-explain.json`には最新テレメトリ取得クエリの実行計画を保存する。生の結果はサイズが大きく機体ごとの明細を含むためGit管理外とし、本書へ集約値を残す。
