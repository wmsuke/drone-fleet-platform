# v0.4.0

Phase 4で、複数機体の操作と結果・異常・運用記録の追跡を追加した。ローカルCompose構成を維持する。この文書は対象機能のまとめであり、Git tagやGitHub Releaseの発行は別作業とする。

## 変更点

- group・membershipのAPIと画面、revision、論理削除
- 対象スナップショットとIdempotency-Keyによる複数機体command受付、機体別outbox
- ACK v3の実行開始・成功・失敗・結果不明通知、SQLiteとPostgreSQLへの保存
- 対象ごとの結果と全体の集約API・画面、期限・後着結果による再評価
- OFFLINE・低battery・command不成功のalert、一覧・詳細・確認APIと画面
- 操作・状態変更と同時commitするaudit log、検索・閲覧と関連リンク
- #146の10/100台負荷検証と1,000台追加確認、#147のgroup操作・alert・auditのローカルE2EとCI
- 許可したdashboard originからgroupを変更・所属解除できるよう、PATCH / DELETEのCORS事前確認を修正

## デモと確認記録

[複数機体運用デモ](../fleet-demo.md)で、10台を起動し、3台のgroupを作って帰還結果を確認する。simulator停止・復帰でalertの発生、確認しても解除されないこと、回復後の自動解除、audit追跡を試せる。

[#146の実測](../load-testing/fleet-commands.md)では100台が初期基準を満たした。追加1,000台の3試行中1試行で100件の期限切れとtimeoutがあったため、通常上限は100台のまま。telemetry 10,000台の既存検証をcommand性能の根拠にはしない。

[#147のE2E](../fleet-e2e.md)は4対象の成功・実行失敗・期限切れ・未応答と後着成功、対象保持、冪等受付、alert・auditを実HTTP/MQTT/DBで確認した。画面自動操作はTesting Library＋jsdom。実ブラウザ確認は別記録であり、Playwrightは未導入。

## 更新時の注意

command受付・関連workerを止め、DBとsimulatorのSQLiteを退避してからPostgreSQL migrationを適用する。API・ingestor・simulator・alert-evaluatorを同じ実装へ揃えて再開する。Composeは`migrate`終了後に起動する。既存volumeは保持し、更新時に`down --volumes`を使わない。audit検索用索引など通常のCREATE INDEXを含むため、無停止・ローリング更新は保証しない。

MQTT topic・QoS・retainは変更しない。command v2、受領/期限拒否ACK v1/v2と実行通知ACK v3を扱う。旧履歴や旧simulatorの受領ACKから成功を補完しない。SQLiteの旧STARTEDはUNCERTAINとし自動再実行しない。移行順と保存境界は[実行結果通知](../command-results.md)、[alert](../alerts.md)、[audit log](../audit-log.md)を参照する。

## 制約

202は受付、受領ACKは受領、SUCCEEDEDはsimulatorの定義した完了であり、実機の安全を証明しない。開始期限30秒と結果確認期限120秒は別で、未応答は操作未実施の証明ではない。後着結果で全体評価が変わり得る。受付後のキャンセル・自動再実行・全機体同時実行・排他スケジューラはない。

HTTPの認証・権限制御は未実装。操作者はanonymousで、本人性を保証しない。auditに更新・削除APIはないが、DB owner・管理者の改ざん耐性は保証しない。外部通知、保持・archive、署名・WORMも未実装。

Phase 4の横断E2Eと負荷検証はローカルのみ。Phase 2の実AWS経路確認や#64の100台記録を、ACK v3・group・alert・auditの実AWS検証とは扱わない。実機、OTA、ROS 2は後続Phaseの対象である。
