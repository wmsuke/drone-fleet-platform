# v0.6.0：ROS 2 Bridgeと復旧の追跡

Phase 6（#188、#189〜#199）のローカルROS 2参照連携をまとめる。Git tag / GitHub Releaseの発行ではなく、Bridge packageの0.5.0とも別の機能区分である。

## 利用できること

- 固定Ubuntu 24.04 / ROS 2 Jazzy / Fast DDS / Python rclpyのarm64/amd64参照環境。
- LOCAL位置・battery・diagnosticsのtelemetry v3変換、永続バッファ・DB保存receiptと画面追跡。
- Capability Profile・実package/source/runtime/policyの報告と、command実行時の不変構成参照。
- RETURN_HOME専用Action、受領/goal受付/feedback/終端/停止観測の分離、SQLite journalと元UUID GetResult照会。
- 理由付き特定goal cancel、10秒の確認期限、介入/auditと不確定・停止未確認の人間引き継ぎ。
- ROS/MQTT切断、Bridge/Action server再起動、機体側拒否と過去構成保持の実DDS/MQTT障害E2E。

[起動・帰還・中断・世代喪失のデモ](../ros-demo.md)を入口とする。通常の10台simulatorとopt-in OTAは維持する。ROS経路の更新順、永続データの扱いと削除範囲はデモ第5〜6節を参照する。

## 検証と限界

[#198の障害E2E](../ros-e2e.md)と[#210の実測/CI記録](https://github.com/wmsuke/drone-fleet-platform/pull/210)は、native Linux ARM64/AMD64で33ケース・結果/構成/介入件数・cleanupを照合した。#199のデモは`corepack pnpm test:ros-demo`で再現し、当該PRで最新のROS専用checkと通常品質checkを記録する。過去の成功を今回の未実行checkの代わりにしない。

HTTP 202、ACK、ROS受付や再接続は完了ではない。停止観測があっても参照モデル内の証拠であり物理安全停止ではない。result cacheはserver restartで失われ、journal破損・容量超過・時計不信・結果不明を自動再投入で救済しない。exactly-once実行、操作者の本人性、費用や未報告の人間作業時間は保証しない。

独自C++アプリは追加せず、Python/rclpyとinterface生成のament_cmakeを使う理由は[デモ第7節](../ros-demo.md#7-検証記録と後続phase)に記す。Phase 7の実シミュレータ・Task評価、Phase 8のmodel/KPI、実機・実AWS ROS経路・大規模性能は実装/検証済みに含めない。設計の正は[ADR 0008](../adr/0008-ros2-bridge-contract-and-recovery.md)。
