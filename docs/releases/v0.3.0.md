# v0.3.0

Phase 3では、SQLiteに保存したtelemetryとPostgreSQLのcommand outboxを起点に、通信断・プロセス再起動からの復旧を追加した。ローカルMosquitto構成は引き続き利用できる。

## 変更点

- telemetry v2の`sessionId`と、機体・session・sequence単位のDB重複排除
- simulatorのSQLite永続バッファ、上限超過の破棄記録、再接続・再送のバックオフと速度制限
- DB commit後のtelemetry receiptと、保存確認後だけの端末行削除
- command / ACK v2、30秒の操作開始期限、端末の永続的な操作履歴とACK再送
- commandとoutboxの同一transaction保存、API停止後の同じcommandId再送、滞留・試行数の監視API
- 通信断・強制停止・重複・期限切れ・容量超過を組み合わせた復旧E2EとCIログ保存

APIの202は受付完了であり、MQTT送信や機体受領の確認ではない。ACKも受領を示し、操作の完了通知ではない。

## デモと検証

まず[復旧デモと運用制約](../recovery-demo.md)の専用Compose構成で、蓄積・停止・旧session再送・新session生成を確認する。`pnpm test:recovery`でcommand outboxや容量超過も自動検証できる。

[#115 / PR #133](https://github.com/wmsuke/drone-fleet-platform/pull/133)ではローカル実サービスで連続2回成功し、CIの復旧E2Eも成功した。実測件数と識別子、STARTED直後の停止境界fixtureの扱いは[検証記録](../recovery-e2e.md)を参照する。

## 更新時の注意

command受付を止め、PostgreSQL migrationを適用し、ingestor・simulator・APIを揃えて更新する。SQLiteとPostgreSQLのvolumeは保持し、`down --volumes`で既存データを消さない。古いAPIと新しいsimulatorを混在させるローリング更新は対象外である。

旧telemetry v1は保存できるが、receiptと永続的な重複排除の対象ではない。新しいsimulatorは期限なしのv1 commandを実行しない。過去のcommandをoutboxへ移して再実行することはない。詳細は[commandの移行](../command-durability.md#移行と検証)を参照する。

## 保証と対象外

SQLite commit済みtelemetryを、容量・永続領域・通信・DB・receiptの復旧条件の範囲でat-least-once保存する。容量超過、ディスク故障、volume削除、時計ずれ、操作開始後の結果不明を無条件に救済するものではない。exactly-once配送・実行、HTTP受付のidempotency key、実機操作完了、自動アラートは保証・実装していない。

v0.3.0の復旧経路はローカルで検証した。Phase 2の実AWS記録をPhase 3の障害注入結果とは扱わない。実AWSでのreceipt・outboxを含む復旧E2E、実機、証明書自動ローテーション、OTA、ROS 2は対象外または未検証である。新しいAWSリソースやGitHub Release、Git tagの作成はこの文書化には含めない。
